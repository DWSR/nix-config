## Relative locks and source capture

- Stock Nix [2.26 release notes](https://nix.dev/manual/nix/2.26/release-notes/rl-2.26#release-2260-2025-01-22) describe local paths relative to their owning flake. In a synthetic stock Nix 2.34.9 probe, root `path:./flakes/a` and sibling `path:../b` evaluated with an unchanged lock; the lock used `parent` edges and did not hash the area subtrees. Editing B changed both selected outputs without rewriting the lock.
- The same graph evaluated from a captured repository using `path:<repo-source>?dir=flakes/a`. `path:<repo-source>/flakes/a` captured only A and could not resolve B. A Git-backed `./flakes/a` retains the Git source tree and requires tracked files; see stock Nix's [relative-path tests](https://github.com/NixOS/nix/blob/2.35.6/tests/functional/flakes/relative-paths.sh).
- Lix 2.95.4 rejected the stock parent-relative lock as `lock file contains mutable lock`. Its legacy resolver's in-memory lock failed in a fresh store; a warmed store could return stale sibling bytes. A successful warm test is not compatibility evidence. The existing Fly check imports the fixture's `outputs` directly at `flake.nix:5082–5092`; it does not exercise the fixture lock reader.
- Stock Nix honored a composed `follows` pin and a different standalone pin in the probe. An existing root lock can retain old transitive pins after an area's lock edits. `--no-write-lock-file` does not establish that the in-memory graph equals the committed graph; compare `nix flake metadata --json`'s effective `locks` too.

## Engine release and operational constraints

- The [official installer](https://nixos.org/nix/install) served stock Nix **2.36.0** during research, corroborated by the [upstream release tag](https://github.com/NixOS/nix/releases/tag/2.36.0). The download page still advertised 2.35.6. The pinned base/unstable package sets evaluated to `nixVersions.latest` **2.35.3** and did not expose `nix_2_36`; a nixpkgs alias alone does not select the latest official stable release.
- [A nixpkgs revision carrying 2.36.0](https://github.com/NixOS/nixpkgs/commit/630d015caca0160317b7ec234497983429359f04) and the [tagged upstream package output](https://github.com/NixOS/nix/blob/2.36.0/flake.nix) are candidates for an isolated package pin. Neither candidate closure has been built for this spec.
- The running Lix daemon was distinguishable from the shell binary via the daemon socket version. Stock Nix 2.36 exposes the remote version through [`nix store info --store daemon --json`](https://github.com/NixOS/nix/blob/2.36.0/src/nix/store-info.cc). The CLI evaluates lock graphs. The guest daemon supplies builds to the sandbox socket; the sandbox's packaged CLI evaluates there. Builder provisioning scripts also evaluate locally on the target. A remote `ssh-ng` build alone does not prove the target's evaluator supports the graph.
- The current store schema and candidate primary schema both read as 10; that does not prove rollback after writes. See [2.35 CA store trace changes](https://nix.dev/manual/nix/2.35/release-notes/rl-2.35#content-addressed-derivations-changes) and [2.36 release notes](https://nix.dev/manual/nix/2.36/release-notes/rl-2.36). No real activation, restoration, or mixed-version remote build was performed.

## Coverage and ownership findings

- `tests/litellm-routing` mixes catalog/affinity logic with scans and assertions against real Fabro and OpenCode consumers. `tests/lima-vm` and `tests/fabro-service` also mix fixture and host checks. Split assertions by what they read, not their current directory name.
- `configurations/fabro-vm/default.nix` composes the shared Postgres cluster, workload schema, Podman, API bridge, `iii`, and sandbox. The API bridge is Fabro dispatch plumbing, not LiteLLM. Guest mount tags come from the personal host's rendered Lima mounts. AgentMemory's `iii-engine` is a separate pin from guest `iii` and workers.
- OpenCode and Pi consume AgentMemory options; AgentMemory consumes MCP integration. Pi and guest OpenCode consume SDD assets. The AgentMemory matrix also executes compaction integration tests. Root ownership of that matrix avoids a reverse area dependency.
- The Fly deployment suite uses local stubs and nested builds that are blocked by the ordinary build sandbox (`flake.nix:5094–5132`). Lima refuses root. Existing filtered CI intentionally does not build the cold OpenCode subset or duplicate `prek` work. `ubuntu-latest` is x64; the [CI runner table](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) identifies ARM Linux runners. Availability and the migrated matrix have not been tested.
- Dependabot's [Nix fetcher](https://github.com/dependabot/dependabot-core/blob/main/nix/lib/dependabot/nix/file_fetcher.rb) reads one manifest/lock pair per directory. No evidence yet that it keeps a changed root pin and every standalone lock synchronized in one update. The current cooldown check inspects only root Nix coverage (`tests/dependency-cooldown/cooldown.test.py:199–239`).

## Approaches evaluated

| Approach | Trade-off |
| --- | --- |
| Extract Nix files but keep a single flake | Smallest engine and lock delta. Does not deliver standalone area flake entrypoints. |
| Independent flake wrappers; root imports ordinary Nix files | Viable on both engines with fixture/injection seams. Requires coordinating pins and composition manually instead of using local flake edges. |
| Stage stock Nix, then compose relative area flakes with compatibility aliases | Supports direct tests and ordinary package/module outputs. Requires a gated engine transition and verified root/area lock parity. |

Effort **XL**, risk **high**: mechanical moves are straightforward, but output parity, operational Nix recovery, and the guest/agent test seams span many files and build contexts. Carry forward native clean-checkout probes, release re-verification, daemon recovery rehearsal, and CI/Dependabot integration tests as implementation evidence, not completed verification.

## Synthesis

- Scope a check by its inputs, not its name or existing directory. The same area output can serve an independent consumer, a CI shard, and a root alias; only the caller context changes.
- Native flake locks and module composition cover the required extension points. A third-party framework or dynamic flake loader would add a second migration without simplifying operator compatibility.
- All heavy host checks need not be rewritten for single-area development. Preserve the integration lane and extract only the local assertions needed to make each area useful. Keep the engine transition, physical moves, and CI policy changes in separately verifiable slices.

## Design validation findings

- Root's generated registry and `/etc/nix/path` map consume all flake inputs (`configurations/common-darwin/default.nix:185–190,251–258`). Area entrypoints cannot be registered as isolated subdirectory store paths.
- The Fly runtime harness uses only the fixture's locked nixpkgs but reads it by evaluating the isolated fixture directory (`tests/fly-app/deploy.test.js:366–370`). Separate recoverable source capture for consumer tests from pinned inputs for stub builds.
- The OpenCode guest imports the LiteLLM catalog and both clients read the Fabro skill by path. Fix those seams before moving consumers; the assignments do not require a reverse dependency.

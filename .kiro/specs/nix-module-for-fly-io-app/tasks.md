# Implementation Plan

- [ ] 1. Validate the Nixpacks-on-Fly remote-builder compatibility gate
  - Identify a supported integration that accepts the selected Nix derivation output and builds it with Nixpacks on a Fly remote builder; record the concrete interface and reproducible evidence.
  - Do not substitute a local image build, ordinary Fly buildpacks, or an undocumented builder path.
  - Done when the supported path is demonstrated; if it cannot be demonstrated, stop implementation and request an upstream requirement decision rather than claiming derivation support.
  - _Requirements: 3.2, 3.3, 3.6_

- [ ] 2. Define the reusable NixOS module and secret-free declaration contract
- [ ] 2.1 Add the module interface and export it from the flake
  - Create `modules/fly-app.nix` with options for an existing app identity, app settings, complete Machine configurations, and exactly one image-source choice: an existing image or a Nix derivation.
  - Keep Machine configurations open to JSON-compatible Fly API fields, including `containers`; expose the module as a reusable flake output.
  - Done when a representative app and multi-container Machine evaluate through the exported module interface.
  - _Requirements: 1.1, 1.2, 1.3, 2.1, 2.3_
- [ ] 2.2 Validate declarations and render the store-safe deployment specification
  - Reject conflicting image sources and a missing required image source with option-specific evaluation errors; reject non-JSON-compatible app or Machine values.
  - Render a deployment specification containing app, Machine, and image-source declarations without a token or runtime credential path.
  - Done when valid fixtures serialize all declared fields and invalid image-source fixtures fail during evaluation.
  - _Requirements: 1.3, 3.4, 3.5, 6.1, 6.2, 6.3_

- [ ] 3. Implement the Fly deployment runtime
- [ ] 3.1 Render Fly app settings and complete Machine configuration
  - Render declared app settings to runtime `fly.toml` and each full Machine config to JSON referenced by the documented deploy path.
  - Preserve unmodeled API fields and every declared container; add Fly-required Pilot init configuration when a `containers` array is present without dropping other fields.
  - Do not create or delete app resources or remove undeclared Machines.
  - Done when serialization tests show app settings, arbitrary Machine fields, and multi-container config in the generated inputs.
  - _Requirements: 1.2, 1.3, 1.4, 2.1, 2.2, 2.3, 2.4_
- [ ] 3.2 Resolve image sources and apply the declaration through Fly
  - Use an existing image reference directly; for a derivation, invoke only the Nixpacks/Fly remote-builder integration proven in Task 1.
  - Pass the resolved image and rendered configuration to the documented `flyctl deploy` path; fail on builder or Fly rejection and never claim success after failure.
  - Done when stubbed existing-image, builder-success, builder-failure, and Fly-rejection cases return the specified result.
  - _Depends: 1, 2.2, 3.1_
  - _Requirements: 3.1, 3.2, 3.3, 3.6, 4.3, 4.4_
- [ ] 3.3 Add runtime-only token authentication and redacted errors
  - Read `FLY_API_TOKEN` from the runtime environment, reject absent or empty values before API calls, and never require interactive `flyctl auth login`.
  - Keep the token out of derivations, store paths, generated files, process arguments, and diagnostics; report authentication, builder, API, and network failures with redacted messages and nonzero status.
  - Done when poisoned-token tests confirm environment-only use and no value appears in generated artifacts, arguments, or captured logs. Follow `design.md`'s `## Operator Provisioning` for operator wiring; do not provision a token.
  - _Requirements: 4.4, 5.1, 5.2, 5.3, 5.4, 6.1, 6.2, 6.3_

- [ ] 4. Integrate deployment with standard NixOS activation and supported systems
- [ ] 4.1 Invoke deployment synchronously from NixOS activation
  - Add the activation integration that invokes the deploy executable with the store-safe specification and runtime `FLY_API_TOKEN`, without passing the token as an argument.
  - Propagate deploy failure as activation failure so deploy-rs and Colmena need no Fly-specific options and cannot report a rejected deployment as successful.
  - Done when activation fixtures prove ordinary NixOS profile activation invokes deployment and propagates its exit status.
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 5.1, 6.1, 6.2, 6.3_
- [ ] 4.2 Export deployment packages for all supported client platforms
  - Expose the deploy executable and checks for `aarch64-darwin`, `x86_64-linux`, and `aarch64-linux` without introducing Fly-specific deploy-rs or Colmena integrations.
  - Done when module evaluation and deploy-package builds succeed for each system and produce equivalent serialized app and Machine configuration.
  - _Depends: 3.2, 4.1_
  - _Requirements: 4.1, 4.2, 7.1, 7.2, 7.3, 7.4_

- [ ] 5. Verify module, runtime, and deployment behavior
- [ ] 5.1 Add module evaluation and serialization tests
  - Cover app identity/settings, arbitrary Machine fields, single- and multi-container declarations, Pilot configuration, image-source conflicts, and missing required images.
  - Done when valid fixtures preserve declared configuration and each invalid fixture fails with a useful evaluation error.
  - _Depends: 2.2, 3.1_
  - _Requirements: 1.1, 1.2, 1.3, 2.1, 2.2, 2.3, 3.4, 3.5_
- [ ] 5.2 Add stubbed deployment and secret-safety tests
  - Stub `flyctl` and the builder boundary to cover success, authentication failure, builder failure, Fly rejection, and nonzero activation propagation without a live credential.
  - Scan generated specifications, derivation references, arguments, and captured logs with a fixture token; verify no false success on failed deployment.
  - Done when the test suite proves failure behavior and the fixture token appears in none of the inspected outputs.
  - _Depends: 3.2, 3.3, 4.1_
  - _Requirements: 3.6, 4.3, 4.4, 5.1, 5.2, 5.3, 5.4, 6.1, 6.2, 6.3_
- [ ] 5.3 Register repository checks for deployment-tool compatibility and platform parity
  - Add flake checks for module evaluation, runtime behavior, secret safety, deploy-rs/Colmena standard-activation compatibility, and deploy-client builds on `aarch64-darwin`, `x86_64-linux`, and `aarch64-linux`.
  - Compare serialized deployment specifications across supported systems and assert both tools consume the module without Fly-specific options.
  - Done when the registered checks pass for each supported system and cover both deployment-tool consumers.
  - _Depends: 4.1, 4.2, 5.1, 5.2_
  - _Requirements: 4.1, 4.2, 7.1, 7.2, 7.3, 7.4_
- [ ] 5.4 Add end-to-end acceptance tests with deployment stubs
  - Exercise an existing-image single-container and multi-container deployment, changed settings, and rejected deployment through the activation path using stubbed `flyctl` and a fixture token.
  - Done when tests verify serialized settings and Machine config reach the deploy command, success follows acceptance, failures return nonzero, and no token value is logged.
  - _Depends: 4.1, 5.1, 5.2_
  - _Requirements: 1.4, 2.4, 3.6, 4.3, 4.4, 5.4_
- [ ]* 5.5 Run live acceptance against an existing Fly app
  - Provide an operator-run checklist for single-container and multi-container deployments, changed settings, and a rejected deployment; use the token only through the runtime environment described in `design.md`'s `## Operator Provisioning`.
  - Done when the checklist records Fly-observed declared settings and Machine configuration, or records the live run as unavailable; never provision or record token values.
  - _Depends: 1, 3.3, 4.1, 5.4_
  - _Requirements: 1.4, 2.4, 3.6, 4.3, 4.4, 5.4_
